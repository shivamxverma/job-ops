## 3.1 Why do you want to work here?

I read your code before writing this. openalex-api-proxy, the Worker in front of api.openalex.org, is the part I keep going back to. Every request gets priced, counted in a Durable Object, refunded when it shouldn't have cost anything, and the prepaid part gets settled into Postgres later. That's a credit ledger. I built one at klimb.io across 6+ AI features, in plain Postgres, and yours is the harder version: the counting happens at the edge and the balance lives somewhere else.

The problems I like are the ones where data has to stay right while a lot is moving: the same entity arriving from several sources, a hash deciding what changed, a count that has to add up. In Hireflow the same job shows up on LinkedIn, Wellfound, YC and Telegram with different titles, and I dedupe it with SHA-256 fingerprints of the normalised fields. At poiro.com I put fail-closed spend caps on third-party APIs (500 calls per org per day, 5,000 globally), because a cap that fails open is just a suggestion. Reading walden's notes on content hashes re-stamping tens of millions of works was the same idea at a scale I haven't worked at yet, and that's the point.

The other reason is how you work. "Notice what's missing, propose it, build it, ship it, and answer the tickets about it" is the job I want, and I'd rather do it where the output serves a billion API calls a month.

And the mission doesn't need dressing up. An open index of research, free to anyone, including a student in India who can't pay for Scopus.

## 3.3 What's the coolest thing you've ever built?

CodeSM, a code execution engine that runs untrusted submissions in C, C++, Java, Go, Python and JavaScript without taking the host down. It's live at code-sm.vercel.app.

The hard part isn't running code, it's running code that's trying to hurt you: fork bombs, infinite loops, network calls. Each submission runs in Docker with no network, a read-only root filesystem, all capabilities dropped, no-new-privileges, 256 MB of memory, 32 processes, half a CPU and a timeout. Grading happens on a BullMQ + Redis queue, so the API returns as soon as the submission is saved.

The decision I'm happiest with is how a submission meets its test cases. A fresh container per test case is the easy design and the slow one. I start one container per submission, run every test case inside it with docker exec, then destroy it. Test data comes from S3 one case at a time with early exit on the first failure, so per-job memory stays bounded however big the test set is. I also moved it from MongoDB to Postgres, with one Drizzle schema shared by the API and the workers.

A close second is Hireflow, because it's closer to your data problems. It pulls job listings from LinkedIn, Wellfound, YC and Telegram, and the same job shows up in several places with different titles and formatting. I dedupe them with SHA-256 fingerprints of the normalised title, company and description. It also uses an LLM to rewrite resume bullets, with a validator that rejects any skill the model adds that isn't in the real profile. I didn't trust the model not to make things up, so I made it unable to.
